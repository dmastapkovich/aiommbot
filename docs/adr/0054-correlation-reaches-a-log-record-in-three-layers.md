# A correlation identifier reaches a log record through three layers — the call's own `extra`, the name of the asyncio task, and a Core `ContextVar` with a filter the application attaches — and never through the process-global record factory

A retry line written by the API client holds a `request_id` and no `Event`, so on its own it cannot
be tied to the delivery that caused it — and that join is what makes a log worth reading. The
standard library offers four mechanisms for ambient context and three of them are wrong for a
library: `LoggerAdapter` "ignore[s] the *extra* argument of individual log calls" unless
`merge_extra=True`, added in 3.13 and therefore unavailable on the 3.12 floor of
[ADR-0008](0008-python-floor-3-12-with-typing-extensions.md); `Formatter` is the application's
object; and `setLogRecordFactory` is one process-global slot already claimed by
`opentelemetry-instrumentation-logging`
([`docs/research/24`](../research/24-library-logging-design.md) §1, §5). We decided three layers,
each doing only what it alone can:

- **The call's own `extra`** is the base. Every record carries the identifiers its call site already
  holds — `correlation_id`, `kind`, `handler`, `operation`, `attempt`, `request_id`,
  `connection_id`, `seq` — passed through `extra=` and never interpolated into the message
  (`ST-LOG-05`). This layer cannot be broken by configuration, survives a `QueueHandler`, and is
  machine-readable to structlog, `python-json-logger` and a plain `Formatter` with no adaptation
  from us ([`docs/research/24`](../research/24-library-logging-design.md) §6).
- **The name of the asyncio task** carries the delivery to records the framework did not write. The
  Dispatcher names the task it runs a delivery in after that delivery, and `taskName` — filled from
  `asyncio.current_task().get_name()` at record creation since 3.12, exactly our floor — then
  appears on **every** record emitted inside it, including records from `httpx2` and `websockets`,
  which no filter of ours could ever reach. It costs one string per delivery, no dependency and no
  code at the logging site.
- **A Core-owned `ContextVar` holding the CorrelationId**, with a **callable filter object the
  framework ships and the application attaches to its handler**. The contextvar is the source of
  truth and is injectable; the filter is how the value reaches a record whose call site did not have
  it. It attaches to a **handler**, not to our logger, because "events which have been generated by
  descendant loggers will not be filtered by a logger's filter setting". It is a plain callable
  rather than a `logging.Filter` subclass — "you can use a function (or other callable) as a
  filter" — which is also what keeps inheritance on Protocol seams only
  ([ADR-0006](0006-architectural-tenets-of-the-core.md)); and because a filter may return a
  replacement record since 3.12, it adds the field "without having side effects on other handlers".
  The glossary reserves **Filter** for a predicate over an Event, so the term for this is **Log
  correlation** and the name is not a Filter.
- **`setLogRecordFactory` is never ours**, and neither are `otelTraceID` and its siblings: the
  recognised division is that the application installs the OpenTelemetry logging instrumentation
  that owns the slot, and the documentation says so instead of us competing for it.
- **The Sync executor copies the context explicitly.** `loop.run_in_executor` documents no
  `contextvars` propagation — `asyncio.to_thread` does, and it is not what
  [ADR-0030](0030-synchronous-callables-by-explicit-declaration.md) uses — so a synchronous Handler
  reaches its thread with a copied context, which ADR-0030 already requires, and `taskName` does not
  reach it at all because a thread has no current task.

## Considered options

- *A `get_logger()` factory returning a `LoggerAdapter` carrying the context, on the model of
  Celery's `get_task_logger`* — rejected: on Python 3.12 every per-call field is silently dropped,
  and the per-call fields are the point.
- *A `Formatter` subclass that injects the context, which is Celery's actual mechanism* — rejected:
  it only works when the application installs our formatter, which is a configuration we do not own.
- *Explicit `extra` only, as Django does* — rejected: it is the simplest and it leaves the case the
  requirement named — an API retry inside a handler — unjoined.
- *Wrapping the record factory ourselves, chaining the previous one* — rejected: one slot, one
  owner, and the other owner is the application's own instrumentation.

## Consequences

- The filter callable, the contextvar accessor and the task-name format are public names on Core
  package paths ([ADR-0042](0042-a-public-name-is-documented-at-its-package-path.md)); the
  task-name format is part of the contract of
  [ADR-0053](0053-log-records-are-a-documented-contract.md), because an operator will grep it.
- The executable `dictConfig` example of ADR-0053 shows the filter attached to a handler and
  `%(taskName)s` in the format, since both are inert unless the application asks for them.
