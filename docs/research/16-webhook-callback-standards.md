# Webhook callback handling, authenticity and replay protection — standards, Mattermost guidance, peer practice

Status: complete (2026-09-03). Resolves GitHub issue #51. Mattermost sources are `master` of github.com/mattermost/mattermost (fetched 2026-09-03); code is quoted verbatim where marked as such. "unverified" marks anything not confirmed from a primary source. Builds on `11-webhook-ingress-patterns.md` §6 (callback contract, 30 s `OutgoingIntegrationRequestsTimeout`, `PostActionIntegrationResponse`, `SubmitDialogResponse`, "external callbacks carry no signature") and does not repeat it.

## 0. Answer in three sentences

Mattermost makes **exactly one** HTTP attempt per click or dialog submission, never retries, maps every non-200 to a client-visible error, and caps the body at 1 MiB — so the reply channel must answer inside the admin-configurable 30 s or the user sees "Action failed to execute"; every peer platform with a comparable synchronous reply (Slack, Discord, GitHub) sets a hard 3–10 s acknowledgement deadline and pushes the rest to asynchronous follow-up, which supports the planned "~10 s, then ack and continue" rule. Because the server signs nothing towards an external URL (only `Content-Type`/`Accept`), RFC 9421 and Standard Webhooks are inapplicable as *transport* schemes, but their design — keyed MAC over `id.timestamp.payload`, version prefix, key id, constant-time compare, bounded validity, id-based dedup — is exactly what a **self-issued** token in `context`/`state` should copy; the standards that then govern the token itself are RFC 8725 and ASVS 5.0 V9 (fixed algorithm, validity window, audience/purpose, no trust in received claims). Recommendation: a ~40-line stdlib HMAC-SHA256 compact token (versioned, `kid`, `exp`, action id, optional actor binding) as the core codec, default-on when the transport is enabled with an explicit `off` switch (CISA/OWASP "secure by default"), `pyseto`/PASETO v4 as an optional codec behind the same Protocol rather than a hard dependency, and replay handled as **per-button expiry + handler-level idempotency**, with a nonce store only as an opt-in for single-use buttons.

## 1. Callback handling and reply semantics

### 1.1 Mattermost server: one request, no retry, strict status mapping

`DoPostActionWithCookie` → `DoActionRequest` performs a single `Do` under `context.WithTimeout(OutgoingIntegrationRequestsTimeout)`; there is no loop, no backoff, no re-delivery anywhere in `integration_action.go` ([source](https://raw.githubusercontent.com/mattermost/mattermost/master/server/channels/app/integration_action.go)). The status handling, verbatim:

```go
if resp.StatusCode != http.StatusOK {
    // Preserve 429 and 503 because they carry retry semantics (RFC 6585,
    // RFC 7231) that downstream HTTP clients legitimately need. Map other
    // 5xx responses to 502 Bad Gateway since the failure is upstream of
    // MM. Sanitize all other non-200 responses to 400 so plugin-specific
    // 4xx codes do not leak misleading semantics to MM API clients.
    status := http.StatusBadRequest
    switch {
    case resp.StatusCode == http.StatusTooManyRequests, resp.StatusCode == http.StatusServiceUnavailable:
        status = resp.StatusCode
    case resp.StatusCode >= 500:
        status = http.StatusBadGateway
    }
    return resp, model.NewAppError("DoActionRequest", "api.post.do_action.action_integration.app_error", nil, fmt.Sprintf("status=%v", resp.StatusCode), status)
}
```

Note the comment: 429/503 are *preserved for the Mattermost API client*, not used by the server to retry. Only `200` is success — a `202 Accepted` is an error. After the request:

```go
var response model.PostActionIntegrationResponse
limitedReader := io.LimitReader(resp.Body, MaxIntegrationResponseSize)
respBytes, err := io.ReadAll(limitedReader)
...
if len(respBytes) > 0 {
    if err = json.Unmarshal(respBytes, &response); err != nil {
        return "", "", model.NewAppError("DoPostActionWithCookie", "api.post.do_action.action_integration.app_error", nil, "", http.StatusBadRequest).Wrap(err)
    }
}
```

An **empty body is valid** for actions as well as dialogs; malformed JSON is a 400. The limits live in `webhook.go`: `MaxIntegrationResponseSize = 1024 * 1024 // Posts can be <100KB at most, so this is likely more than enough` and `MaxDialogResponseSize = 1024 * 1024 // 1MB limit for dialog responses to prevent OOM attacks` ([source](https://raw.githubusercontent.com/mattermost/mattermost/master/server/channels/app/webhook.go)). Reading is truncated, not rejected, so an over-long body fails as invalid JSON. The client receives `PostActionAPIResponse{Status: "OK", TriggerId, GotoLocation}` ([api4](https://raw.githubusercontent.com/mattermost/mattermost/master/server/channels/api4/integration_action.go)).

Client-visible effect (docs, v10.5+): "When an action button integration fails, Mattermost automatically displays an error message to the user below the interactive content"; default text "Action failed to execute"; listed triggers: network failure, unreachable URL, non-200 status, invalid JSON ([Interactive messages](https://developers.mattermost.com/integrate/plugins/interactive-messages/)). The docs also show a custom `{"error": {"message": "..."}}` response — the `PostActionIntegrationResponse` struct fetched from `master` has no `Error` field, so how that message reaches the client is **unverified**. The admin knob is documented as "Integration request timeout — The number of seconds to wait for external integration HTTP requests before timing out, including custom slash commands, outgoing webhooks, interactive messages, and interactive dialogs" ([docs](https://docs.mattermost.com/administration-guide/configure/integrations-configuration-settings.html)); the config key is `ServiceSettings.OutgoingIntegrationRequestsTimeout`, default constant `OutgoingIntegrationRequestsDefaultTimeout = 30` ([config.go](https://raw.githubusercontent.com/mattermost/mattermost/master/server/public/model/config.go)). Neither the developer docs nor the forum give "long-running action" guidance; the only field evidence is a plugin issue whose log shows the timeout signature `DoActionRequest ... Client.Timeout exceeded while awaiting headers` surfacing as `http_code: 400` ([mattermost-plugin-remind #120](https://github.com/scottleedavis/mattermost-plugin-remind/issues/120)).

Dialogs: `SubmitInteractiveDialog` uses the same `DoActionRequest`, `io.LimitReader(resp.Body, MaxDialogResponseSize)`, and sets `Type = "dialog_submission"` unless it is `"refresh"` (a newer refresh flow; semantics unverified). The api4 handler checks only that the session can read the channel/team; the server has no notion of "this dialog was already submitted".

New in `master` (heads-up for payload typing, unverified beyond identifiers): `DoPostActionRequest` carries `integration_format` with constants `attachment | apps_binding | block | card | mm_block`, and an `MmBlocksActionCookie` behind `FeatureFlags.MmBlocksEnabled`; for block formats the server forces `Type = "button"` and fills `Context` from the block.

### 1.2 The `PostActionCookie`: what "context is kept confidential" actually rests on

The docs promise: "An important property of the context parameter is that it's kept confidential. If your integration is not behind a firewall, you could add a token to your context without users ever being able to see it" ([docs](https://developers.mattermost.com/integrate/plugins/interactive-messages/)). For **regular posts** that holds because the action definition stays server-side and the client only sends `post_id`/`action_id`; the api4 handler checks `SessionHasPermissionToReadPost`. For **ephemeral posts** there is no stored post, so the server ships the action definition *to the client* inside a cookie: "The clients should hold on to it, and include it with subsequent DoPostAction requests. This allows the server to access the action metadata even when it's not available in the database, for ephemeral posts" ([model](https://raw.githubusercontent.com/mattermost/mattermost/master/server/public/model/integration_action.go)). The cookie contains `Integration *PostActionIntegration` — i.e. **our URL and our `context`** — sealed with AES-GCM under a random 32-byte server secret (`SystemPostActionCookieSecret{Secret []byte}` stored under system key `"PostActionCookieSecret"`, [system.go](https://raw.githubusercontent.com/mattermost/mattermost/master/server/public/model/system.go); generation site in the app package not located in this pass — unverified). `AddPostActionCookies` is applied in `SendEphemeralPost`/`UpdateEphemeralPost` ([post.go](https://raw.githubusercontent.com/mattermost/mattermost/master/server/channels/app/post.go)); the api4 handler decrypts with `model.DecryptPostActionCookie(actionRequest.Cookie, c.App.PostActionCookieSecret())`, then requires `cookiePostId == c.Params.PostId` and read permission on the cookie's channel.

Trust consequences for us:

- Confidentiality of `context` on ephemeral buttons is as strong as AES-GCM under the server's secret — fine, but it is the *server's* property, and `EncryptPostActionCookie` returns the **plaintext** when `len(secret) == 0` (verbatim: `if len(secret) == 0 { return plain, nil }`); whether an empty secret can occur in practice is unverified.
- The cookie has **no timestamp**: a client can re-submit an ephemeral button for as long as the server secret lives. Only a token we issue can expire a button.
- CVE-2024-2447 (GHSA-wp43-vprh-c3w5): Mattermost "fail[s] to authenticate the source of certain types of post actions, allowing an authenticated attacker to create posts as other users via a crafted post action" (fixed 8.1.11/9.3.3/9.4.4/9.5.2, CVSS 7.1) ([advisory](https://github.com/advisories/GHSA-wp43-vprh-c3w5)). The server-side trust boundary has already failed once; `user_id` in the callback is only as trustworthy as the server release.

### 1.3 Acknowledgement latency across vendors and the deadline rule

| Platform | Sync deadline | Consequence of missing it | Retry by sender | Async follow-up channel |
|---|---|---|---|---|
| Mattermost actions/dialogs | 30 s default (admin-configurable) | client error "Action failed to execute"; dialog errors lost | **none** | REST: update post, ephemeral post; no `response_url` |
| Standard Webhooks | "A recommended request timeout value for webhooks is somewhere between 15 and 30s"; success = "2xx" | retry | exponential backoff + jitter | n/a |
| Stripe | "Quickly returns a successful status code (2xx) before any complex logic that might cause a timeout" | "(Timed out) ERR ... defer complex logic" | up to 3 days, backoff | fetch object from API |
| GitHub | "respond with a 2XX response within 10 seconds ... GitHub terminates the connection and considers the delivery a failure" | failure | manual redelivery | queue + API |
| Slack interactivity | "HTTP 200 OK ... within 3 seconds"; `trigger_id` "expire in three seconds", single use | "the Slack user ... will see an error message" | none | `response_url` "up to 5 times within 30 minutes" |
| Discord | "acknowledge the interaction within 3 seconds" | token invalidated | none | deferred response types; token "valid for 15 minutes" |
| Telegram callback | no number; "clients will display a progress bar until you call answerCallbackQuery" | spinner | webhook non-2xx retried | any Bot API call |

Sources: [Standard Webhooks](https://raw.githubusercontent.com/standard-webhooks/standard-webhooks/main/spec/standard-webhooks.md), [Stripe](https://docs.stripe.com/webhooks), [GitHub](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks), [Slack](https://docs.slack.dev/interactivity/handling-user-interaction), [Discord](https://docs.discord.com/developers/interactions/receiving-and-responding), [Telegram](https://core.telegram.org/bots/api) (text mirrored at [grammY](https://grammy.dev/ref/types/callbackquery)).

**Deadline rule distilled.** Every platform that lets the reply carry UI (Slack, Discord) fixes a *short* sync window and moves everything else to a follow-up channel; platforms without UI in the reply (GitHub, Stripe) want a bare 2xx immediately. Mattermost is a hybrid: the reply may carry `update`/`ephemeral_text`/dialog `errors`, has no follow-up URL, no retry, and the *only* way to return dialog field errors is the sync body. Hence: `reply_deadline` must be well inside the server timeout with margin for network and admin tuning — 10 s (one third of 30 s, equal to GitHub's hard limit) is defensible as default; at the deadline send the default empty `200` (accepted by both callback kinds) and continue the handler, whose later effects go through REST (`update_post`, ephemeral post) — the Mattermost analogue of Slack's `response_url`. The handler needs a typed signal that its reply was already sent ("acked late") because dialog `errors` after that point are unrecoverable; anything that must validate a dialog must do so before the deadline.

## 2. Authenticity

### 2.1 Transport-level standards and why they cannot apply here

RFC 9421 defines the **Signer** as "the entity that is generating or has generated an HTTP message signature", carried in `Signature-Input`/`Signature` with parameters `created`, `expires` (both recommended), `nonce`, `keyid`, `alg`; body coverage needs RFC 9530 `Content-Digest`, which "alone does not prevent malicious modification" ([RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html), [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html)). Standard Webhooks signs `msg_id.timestamp.payload` with HMAC-SHA256, `v1,` + base64 in `webhook-signature` (space-delimited list, so "the webhook is signed both using the current key, and using an old key ... and both signatures are sent"), secret `whsec_` + base64, optional `v1a,` Ed25519; consumers "use a constant time comparison function", verify the timestamp "within some allowable tolerance" (reference Python library: `timedelta(minutes=5)`, "Message timestamp too old"/"too new"), and "use the `webhook-id` header as an idempotency key" ([spec](https://raw.githubusercontent.com/standard-webhooks/standard-webhooks/main/spec/standard-webhooks.md), [python impl](https://raw.githubusercontent.com/standard-webhooks/standard-webhooks/main/libraries/python/standardwebhooks/webhooks.py)). Mattermost sets only `Content-Type: application/json` and `Accept: application/json` for external URLs and `config.go` has no signing/secret field for outgoing integrations (checked for `Signature`, `Secret`, `HMAC`, `PostActionCookie`), so **none of these headers will ever arrive**. Slack (`v0:{timestamp}:{body}`, 5 minutes), GitHub (`sha256=` HMAC of body, no timestamp), Discord (Ed25519 over `timestamp + body`, 401 on failure, and "Discord will also perform automated, routine security checks against your endpoint, including purposefully sending you invalid signatures") are the same pattern and equally unavailable ([Slack](https://docs.slack.dev/authentication/verifying-requests-from-slack), [GitHub](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), [Discord](https://docs.discord.com/developers/interactions/overview)).

What survives is the *shape*: the receiver can only trust a MAC/signature over data bound to the message, computed under a key the sender never had — and here the "sender" of the secret is the bot itself, at **button-build time**. The signed content is therefore the button's identity (action id, optionally post/channel/intended user) plus issue time, and the check is an expiry rather than a 5-minute delivery tolerance.

### 2.2 Token formats for a self-issued context secret

**JWT/JWS.** Compact `BASE64URL(header).BASE64URL(payload).BASE64URL(signature)`; `alg` "MUST be present"; `kid` "is a hint indicating which key was used" ([RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html)). Claims: `exp` "MUST NOT be accepted for processing" after, with leeway "usually no more than a few minutes"; `jti` "can be used to prevent the JWT from being replayed"; `aud` — "if not present ... the JWT MUST be rejected" when required ([RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)). RFC 8725 BCP: 3.1 "Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms"; 3.3 "the entire JWT MUST be rejected if any fail"; 3.9 audience; 3.11 explicit `typ`; 3.12 mutually exclusive validation rules; threat: `alg: none` and RS256→HS256 key confusion ([RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)). OWASP ASVS 5.0 V9 restates this as L1: 9.1.1 validate signature/MAC, 9.1.2 algorithm allowlist "must not include the 'None' algorithm", 9.1.3 trusted pre-configured key material, 9.2.1 validity time span; L2: 9.2.2 type/purpose, 9.2.3 audience ([ASVS V9](https://raw.githubusercontent.com/OWASP/ASVS/master/5.0/en/0x18-V9-Self-contained-Tokens.md)). Lesson: a self-issued token should have **no negotiable algorithm at all** — a version byte, not an `alg` header.

**PASETO v4.** "Paseto only allows secure operations. JWT gives you 'algorithm agility', Paseto gives you 'versioned protocols'" ([spec README](https://github.com/paseto-standard/paseto-spec)). `v4.local`: XChaCha20 + keyed BLAKE2b, 32-byte key, 32-byte random nonce, optional footer (where `kid` belongs) and **implicit assertions** — "optional additional authenticated data that IS NOT stored in the token, but IS USED to calculate the authentication tag" ([Version4](https://github.com/paseto-standard/paseto-spec/blob/master/docs/01-Protocol-Versions/Version4.md), [Rationale](https://raw.githubusercontent.com/paseto-standard/paseto-spec/master/docs/Rationale-V3-V4.md), [Claims](https://github.com/paseto-standard/paseto-spec/blob/master/docs/02-Implementation-Guide/04-Claims.md)); `v4.public` = Ed25519. Implicit assertions are the textbook tool for **actor binding** (bind `user_id`/`post_id` without shipping them). Python: `pyseto` 1.10.0 (2026-07-19, Python ≥3.10, `Typing :: Typed`, all versions/purposes + PASERK), but depends on `cryptography<52,>=42`, `pycryptodomex`, `argon2-cffi`, `iso8601` ([PyPI](https://pypi.org/pypi/pyseto/json)); `paseto` 2.0.0 (2024-06-04, releases 2018 → 2021 → 2024, deps `pysodium` (libsodium), `pendulum`, `pycryptodomex`, classifiers up to 3.12) ([PyPI](https://pypi.org/pypi/paseto/json)).

**itsdangerous** 2.2.0 (2024-04-16; Pallets; zero deps; `Typing :: Typed`; 16 KB wheel) ([PyPI](https://pypi.org/pypi/itsdangerous/json)). `TimestampSigner` "records the time of the signing and can be used to expire signatures"; `unsign(..., max_age)` raises `SignatureExpired`; `URLSafeTimedSerializer` = JSON + zlib + base64url; key rotation since 2.0: "a list of keys ... oldest to newest. The newest key is used for signing, all keys are tried for unsigning"; `salt` "is combined with the secret key to derive a unique key for distinguishing different contexts"; default digest **SHA-1** ("When used as the intermediate, iterated step in HMAC, SHA-1 is not insecure") with `digest_method` override; `verify_signature` uses `hmac.compare_digest` ([docs](https://itsdangerous.palletsprojects.com/en/stable/), [changes](https://itsdangerous.palletsprojects.com/en/stable/changes/)). Gaps: no `kid` (rotation = try every key), no claims model (audience/actor must be encoded by the caller), timestamp is issue time only (expiry is a verifier parameter, not in the token).

**Fernet**: AES-128-CBC + HMAC-SHA256, 64-bit timestamp, `decrypt(token, ttl)`, `MultiFernet.rotate` ([spec](https://github.com/fernet/spec/blob/master/Spec.md), [cryptography](https://cryptography.io/en/latest/fernet/)); requires `cryptography` (50.0.1: manylinux wheel 4.7 MB) ([PyPI](https://pypi.org/pypi/cryptography/50.0.1/json)). Encryption buys nothing here: `context` is already confidential per Mattermost and the payload is not secret. **Branca**: XChaCha20-Poly1305, base62, creation timestamp so "the consuming side [decides] how long tokens are valid" ([spec](https://github.com/tuupola/branca-spec)); `pybranca` 0.5.0, last release 2021-08 — stale.

**stdlib**: `hmac.digest(key, msg, 'sha256')` (3.7+), `hmac.compare_digest` ("designed to prevent timing analysis"; leaks only length/type), `base64.urlsafe_b64encode` ([hmac docs](https://docs.python.org/3/library/hmac.html)). Cost: ~40 lines plus a spec; risk is protocol design, not primitives — mitigated by copying Standard Webhooks' canonical string and shipping test vectors.

### 2.3 Mattermost's own precedents

- `trigger_id` — the server's own self-issued token: ECDSA-SHA256 over `clientTriggerId:userId:millis`, verified with `DecodeAndVerifyTriggerId(key, timeout)` where `timeout` is the 30 s integration timeout (research 11 §6). Expiry **and** actor binding, exactly the shape proposed here.
- Apps framework (deprecated: "Starting with Mattermost v10, the Apps Framework will no longer be supported by the Mattermost server", 2024-08-20; repo "deprecated and no longer maintained") signed proxy→app calls with HS256 JWT in `Mattermost-App-Authorization: Bearer …`, claims `jwt.StandardClaims` + `acting_user_id`, **15-minute expiry**, but only when the manifest set `http.use_jwt: true`; remote webhooks defaulted to `"none"` — "The app can perform its own authentication then" ([forum](https://forum.mattermost.com/t/transition-from-apps-framework-to-plugin-framework-in-mattermost-v10/19330), [pkg.go.dev](https://pkg.go.dev/github.com/mattermost/mattermost-plugin-apps/apps), [uphttp](https://raw.githubusercontent.com/mattermost/mattermost-plugin-apps/master/upstream/uphttp/upstream.go)).
- Plugins: "the Mattermost Server sets the HTTP header `Mattermost-User-Id` when the request is made by an authenticated client ... it's the plugin's responsibility to reject the request" ([best practices](https://developers.mattermost.com/integrate/plugins/components/server/best-practices/)). Not available to external bots.
- Telegram, for contrast: `secret_token` → `X-Telegram-Bot-Api-Secret-Token` (Bot API 6.1) is opt-in; previous advice was a secret path segment — the 0.4.x Fernet hook-path design.

### 2.5 Default-on or optional extension

Evidence for **default-on**: CISA/OWASP definition, verbatim from OWASP Proactive Controls C5: "'Secure-by-Default' means products are resilient against prevalent exploitation techniques out of the box without additional charge. Software should start in a secure state without requiring extensive user configuration, ensuring the default settings are always the most secure option" ([C5](https://top10proactive.owasp.org/the-top-10/c5-secure-by-default/)); OWASP Top 10 A05: "The security settings in the application servers, application frameworks ..., libraries, databases, etc., are not set to secure values" ([A05](https://owasp.org/Top10/2021/A05_2021-Security_Misconfiguration/)); Stripe signs unconditionally and its SDK verifies by default; Discord *enforces* verification by probing. Evidence for **opt-in**: Mattermost Apps (`use_jwt`), Telegram (`secret_token`), ASVS 4.1.5 puts "per-message digital signatures ... on top of transport protections" at **Level 3** only ([ASVS V4](https://raw.githubusercontent.com/OWASP/ASVS/master/5.0/en/0x13-V4-API-and-Web-Service.md)). The opt-in cases share one property: the secret must be exchanged between *two parties*. aiommbot owns **both ends** — it builds the button and receives the click — so the only user-facing cost of default-on is one configured key. Authenticity can still be an *extension point* (a `CallbackTokenCodec` Protocol with the stdlib codec as default and `pyseto` as an extra) without being *off by default*; "optional" should mean pluggable, not disabled.

## 3. Replay and stale actions

### 3.1 What the sources say

- Standard Webhooks: timestamp tolerance (impl. 5 min both directions) + `webhook-id` as idempotency key (above).
- Stripe: "default tolerance of 5 minutes ... Don't use a tolerance value of `0`"; retries get "a new signature and timestamp"; "guard against duplicated event receipts by logging the event IDs"; idempotency keys "up to 255 characters", "removed ... after they're at least 24 hours old", replayed key with different params errors ([webhooks](https://docs.stripe.com/webhooks), [idempotent requests](https://docs.stripe.com/api/idempotent_requests)).
- GitHub: "To protect against replay attacks, you can use the `X-GitHub-Delivery` header to ensure that each delivery is unique per event" (redeliveries keep the value); no timestamp in the signature.
- Slack: "more than five minutes from local time, it could be a replay attack"; `response_url` 5 uses / 30 min; `trigger_id` 3 s, "may only be used once" (`trigger_exchanged`).
- Discord: token 15 min; Ed25519 over timestamp+body.
- IETF `Idempotency-Key`: draft-07 (2025-10-15) is **expired**, never an RFC; still useful vocabulary — "The idempotency key MUST be unique and MUST NOT be reused with another request with a different request payload", UUID recommended, "The resource SHOULD define such expiration policy", 409 "A request is outstanding for this Idempotency-Key", 422 "Idempotency-Key is already used" ([datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/), [txt](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.txt)).
- JWT: `exp` with a few minutes' leeway; `jti` for replay ([RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)); RFC 9421 §7.2.2 recommends `created`/`expires`/`nonce` against signature replay.
- Telegram: `answerCallbackQuery` is mandatory per click — an *ack obligation*, not a replay control.
- Mattermost itself: `trigger_id` 30 s and single purpose; ephemeral cookie never expires; dialog submissions are not de-duplicated server-side (handler check reads only permissions).

### 3.2 Comparison table

| Mechanism | Who sets the window | Window | Scope | Storage needed |
|---|---|---|---|---|
| Delivery timestamp tolerance (Standard Webhooks, Stripe, Slack) | receiver | 5 min | one delivery | none |
| Delivery id dedup (`webhook-id`, `X-GitHub-Delivery`, Stripe event id) | receiver | ≥ retry horizon (Stripe: 3 days) | one event | set of ids |
| Idempotency key (Stripe API, IETF draft) | client | 24 h (Stripe); "SHOULD define" (IETF) | one operation | key → result |
| Interaction token (Discord) / `response_url` (Slack) | platform | 15 min / 30 min × 5 uses | one interaction | none |
| `trigger_id` (Slack 3 s; Mattermost 30 s) | platform | seconds | one dialog open | none |
| Token `exp`/`jti` (JWT, PASETO) | issuer | issuer's choice | one token | `jti` set if single-use |
| Mattermost ephemeral cookie | server | unbounded | one button | none |

### 3.3 Translation into aiommbot policy

The Mattermost situation differs from delivery webhooks in two ways: (a) the token is minted when the **button is built**, possibly days before a legitimate click, so a 5-minute delivery tolerance is meaningless — the right primitive is a **per-button `exp`** chosen by the bot (default generous, e.g. 24 h; `None` allowed for permanent buttons); (b) "the same token twice" is often legitimate (several users click the same post; one user re-clicks), and the callback's `user_id`/`trigger_id` differ per click while the token does not — so **replay is not a transport property**. Hence: expiry in the token; a small **clock leeway** (RFC 7519's "few minutes", e.g. 120 s) for `exp` and for `iat` in the future; **idempotency at handler/service level** (the durable-state rule from ADR-0012/13 and `13-conversation-state-lifetime.md`), with an **optional nonce/`jti` store** behind a Protocol for buttons declared single-use; and a **typed outcome** so the handler can answer "this button has expired" with `ephemeral_text` and disable the buttons via `update` instead of silently doing nothing.

## 4. Recommendation for #20

**Reply semantics and deadline.** One synchronous reply per callback, produced through the payload-bound typed reply channel; default reply = empty `200` (valid for actions and dialogs). `reply_deadline` default **10 s** (rule: strictly less than the smallest realistic `OutgoingIntegrationRequestsTimeout`, leaving ≥ 2/3 of the default 30 s as margin; equals GitHub's hard limit; Slack/Discord's 3 s is unnecessary because Mattermost has no follow-up URL and does allow UI in the reply). At the deadline: send the default reply, mark the context `acked=True`, continue the handler; a later `reply()` returns a typed `ReplyAlreadySent` outcome instead of raising, and side effects go through REST. Enforce the 1 MiB body cap when serialising replies; never return `202`. Document that dialog `errors` are only deliverable before the deadline.

**Authenticity.** Default-on when the webhook transport is enabled; a missing key is a startup error unless `authenticity="off"` is written explicitly (CISA: loosening must be a conscious decision); keep 0.4.x's `strict | warn` for migration. Primitive: a **stdlib HMAC-SHA256 compact token** — `v1.<base64url(payload)>.<base64url(mac)>`, MAC over `"v1" || "." || payload`, no `alg` field (versioned protocol per PASETO, allowlist per RFC 8725 §3.1/ASVS 9.1.2), payload = compact JSON `{kid, iat, exp?, aud (bot id), act (action/callback id), sub? (intended user id), jti?}`, compared with `hmac.compare_digest`, size ≈ 120–160 bytes (well under the ~100 KB post budget; dialog `state` is a free-form string). Key rotation Standard-Webhooks-style: `signing_keys: {kid: secret}` + `active_kid`; verify by `kid`, reject unknown ids (ASVS 9.1.3). Actor binding optional per button (`sub`): mismatch with the callback's `user_id` → `Forbidden` outcome (the server asserts `user_id`; binding defends against a token lifted from a shared post, not against a compromised server). Expose the codec as a `CallbackTokenCodec` Protocol; ship `pyseto` (v4.local, `kid` in footer, implicit assertion = `user_id`) as `aiommbot[paseto]` for teams that want a standardised format. Do not adopt itsdangerous (SHA-1 default, no `kid`, still needs a claims wrapper) or Fernet/Branca (encryption adds nothing; `cryptography`/libsodium weight).

**Replay / stale policy and knobs.** `default_ttl` (per-button override, `None` = no expiry), `clock_leeway` (120 s), `nonce_store: NonceStore | None` (single-use buttons/dialogs only), `enforcement`. Outcomes as a typed union: `Verified(claims)`, `Missing`, `Invalid(reason)`, `Expired(exp, age)`, `Replayed(jti)`, `ActorMismatch`. Handlers receive `Expired`/`Replayed` as a routable stale-action event (default handler: `ephemeral_text` "This action has expired" + `update` disabling buttons) rather than a dropped request; `Invalid`/`Missing` under `strict` end the request with an empty `404` as in 0.4.x, without invoking handlers. Idempotency of business effects stays in services/repositories.

**What to log.** At INFO: outcome class, `kid`, `act`, `post_id`, `channel_id`, `user_id`, token age, reply latency, whether the deadline fired; at DEBUG nothing more. Never the token, `context`/`state` contents, `trigger_id`, or dialog `submission`. Metrics per outcome class (Stripe/Standard Webhooks treat verification failures as operational signals).
