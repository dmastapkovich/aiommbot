# Lifetime and expiry of conversation state — how bot frameworks and stateless designs bound it

Status: complete (2026-09-03). Primary sources only: framework source on the default branch and official docs, quoted verbatim where it matters; "unverified" marks anything not confirmed from a primary source. Builds on `docs/research/07-durable-bot-state-storage.md` (storage shapes) and ADR-0003/ADR-0022 (stateless Core, State plugin with `KeyValueStore` + `LockProvider`, typed `Flow[Data]`, `StaleState`). ADR-0022 left "Lifetime" open pending this ticket.

## 1. aiogram 3

`RedisStorage(redis, key_builder=None, state_ttl: ExpiryT | None = None, data_ttl: ExpiryT | None = None)` — docstring says only "TTL for state records" / "TTL for data records". Both are applied as `ex=` on **every** `SET`: `set_state` does `self.redis.set(redis_key, ..., ex=self.state_ttl)` and `set_data` does `self.redis.set(redis_key, self.json_dumps(data), ex=self.data_ttl)`; `set_state(None)` and `set_data({})` issue `DELETE` instead. So the TTL is **sliding per write**, refreshed on each transition or data write, never on reads. [`aiogram/fsm/storage/redis.py`](https://github.com/aiogram/aiogram/blob/dev-3.x/aiogram/fsm/storage/redis.py). `BaseStorage.update_data` is `get_data` + `dict.update` + `set_data`, so any partial update also refreshes the data TTL. [`base.py`](https://github.com/aiogram/aiogram/blob/dev-3.x/aiogram/fsm/storage/base.py). `FSMContext.clear()` is `await self.set_state(state=None); await self.set_data({})` — the canonical end-of-flow, i.e. explicit deletion of both keys. [`context.py`](https://github.com/aiogram/aiogram/blob/dev-3.x/aiogram/fsm/context.py). Default `None` = no expiry, ever. Event isolation lock: `DEFAULT_REDIS_LOCK_KWARGS = {"timeout": 60}` (redis-py lock auto-release).

`MemoryStorage` has no TTL; its docstring warns "This storage is not recommended for production use, as all data is lost when the bot restarts" — the only lifetime bound is process death. [`memory.py`](https://github.com/aiogram/aiogram/blob/dev-3.x/aiogram/fsm/storage/memory.py). `PyMongoStorage` has no TTL parameter and creates no TTL index (confirmed again against [`pymongo.py`](https://github.com/aiogram/aiogram/blob/dev-3.x/aiogram/fsm/storage/pymongo.py); see also doc 07 §4). The docs page [`storages.rst`](https://github.com/aiogram/aiogram/blob/dev-3.x/docs/dispatcher/finite_state_machine/storages.rst) is autodoc only — **no guidance** on choosing a TTL or on what happens when a state key expires. When it does expire, `get_state()` returns `None` and the update falls through to handlers without a state filter — silent reset, no signal.

## 2. Rasa

Session lifetime is declared **per bot in the domain**: `session_config: session_expiration_time: 60  # value in minutes, 0 means infinitely long` and `carry_over_slots_to_new_session: true`. "if a user sends their first message after 60 minutes of inactivity, a new conversation session is triggered, and that any existing slots are carried over into the new session" … "A session start triggers the default action `action_session_start`. Its default implementation moves all existing slots into the new session … all conversations begin with an `action_session_start`." [`docs/docs/domain.mdx`](https://github.com/RasaHQ/rasa/blob/main/docs/docs/domain.mdx). Constants: `DEFAULT_SESSION_EXPIRATION_TIME_IN_MINUTES = 60`, `DEFAULT_CARRY_OVER_SLOTS_TO_NEW_SESSION = True` [`rasa/shared/constants.py`](https://github.com/RasaHQ/rasa/blob/main/rasa/shared/constants.py).

Expiry is **lazy and inactivity-based**: `MessageProcessor._has_session_expired` takes the last `UserUttered` event and returns `time_delta_in_seconds / 60 > session_expiration_time`; `_update_tracker_session` then runs `action_session_start` "if not tracker.applied_events() or self._has_session_expired(tracker)". [`rasa/core/processor.py`](https://github.com/RasaHQ/rasa/blob/main/rasa/core/processor.py). Nothing is deleted: the tracker (full event log) stays; a session boundary event is appended and slots are re-set. Storage retention is separate: `RedisTrackerStore(record_exp: Optional[float] = None)` ("Record expiry in seconds", [`tracker-stores.mdx`](https://github.com/RasaHQ/rasa/blob/main/docs/docs/tracker-stores.mdx)) does `self.red.set(key, serialised_tracker, ex=timeout)` on every `save` — sliding per write, default none; Mongo/SQL stores have no expiry at all. [`rasa/core/tracker_store.py`](https://github.com/RasaHQ/rasa/blob/main/rasa/core/tracker_store.py). Locks: `DEFAULT_LOCK_LIFETIME = 60  # in seconds`, overridable by env `TICKET_LOCK_LIFETIME`; `lock()` raises `LockError` if the ticket expired. [`rasa/core/constants.py`](https://github.com/RasaHQ/rasa/blob/main/rasa/core/constants.py), [`lock_store.py`](https://github.com/RasaHQ/rasa/blob/main/rasa/core/lock_store.py).

## 3. Microsoft Bot Framework

"As with web apps, a bot is inherently stateless; a different instance of your bot may handle any given turn." Three buckets keyed by channel: `UserState` (`{ChannelId}/users/{From.Id}`), `ConversationState` (`{ChannelId}/conversations/{Conversation.Id}`), `PrivateConversationState` (both). State is loaded on the first accessor `get` of a turn into a per-turn cache and written only by `SaveChanges`; "Bot state implements a 'last write wins' behavior". "In-memory data storage is intended for local testing only as this storage is volatile and temporary." Conversation state is "good for tracking … Whether the bot asked the user a question, and which question that was"; user state for "Non-critical user information". [bot-builder-concept-state](https://learn.microsoft.com/en-us/azure/bot-service/bot-builder-concept-state). Dialog stack: "the dialog's state must be retrieved from and saved to memory each turn. This is handled via a dialog state property accessor defined on the bot's conversation state" — so dialog-stack lifetime equals conversation-state lifetime. [bot-builder-concept-dialog](https://learn.microsoft.com/en-us/azure/bot-service/bot-builder-concept-dialog). The protocol has an `endOfConversation` activity that "signal[s] the end of a conversation from the recipient's perspective". [botframework-activity spec §End of conversation](https://github.com/microsoft/botframework-sdk/blob/main/specs/botframework-activity/botframework-activity.md).

**No TTL in the SDK.** "The Bot Framework SDK doesn't expose a TTL configuration setting." The how-to offers two patterns: (a) *user-interaction expiration* — a `LastAccessedTime` property in conversation state compared to `ExpireAfterSeconds` in `OnTurn`; on expiry send "Welcome back!  Let's start over from the beginning." and `ConversationState.ClearStateAsync`; the timestamp is re-set every turn (sliding); (b) *storage expiration* — create the Cosmos container with `defaultTtl` (sample: 30 s) **for the ConversationState container only, "but not on UserState"**; "Cosmos DB will now automatically delete conversation state records after 30 seconds of inactivity". [bot-builder-howto-expire-conversation](https://learn.microsoft.com/en-us/azure/bot-service/bot-builder-howto-expire-conversation). Blob storage TTL: not covered by the SDK docs (unverified whether any first-party mechanism exists). Python `CosmosDbPartitionedStorage` has no ttl option ([source](https://github.com/microsoft/botbuilder-python/blob/main/libraries/botbuilder-azure/botbuilder/azure/cosmosdb_partitioned_storage.py)).

## 4. Dialogflow CX / ES and Amazon Lex

**Dialogflow CX** — "A session remains active and its data is stored for 30 minutes after the last request is sent for the session." Extend with `QueryParameters.session_ttl` ("The maximum allowed value is 24 hours"), or restore by passing `current_page` and `parameters` on the next request — "Handler call stack will **not** be revived with this approach." Session ID ≤ 36 bytes, generated by the caller. [CX session concept](https://docs.cloud.google.com/dialogflow/cx/docs/concept/session). Sliding on every request; after expiry the caller starts a fresh session (parameters gone) or replays state from the message.

**Dialogflow ES** — contexts carry a **turn counter and a wall-clock cap**: "The default lifespan is five conversational turns for normal intents and two conversational turns for follow-up intents." "all contexts expire after 20 minutes of becoming active." "When an intent is matched with an output context that is already active, the lifespan and expiration timer are reset." [ES input/output contexts](https://docs.cloud.google.com/dialogflow/es/docs/contexts-input-output).

**Amazon Lex V2** — `idleSessionTTLInSeconds` is **required** on `CreateBot`: "A user interaction remains active for the amount of time specified. If no conversation occurs during this time, the session expires and Amazon Lex deletes any data provided before the timeout. You can specify between 60 (1 minute) and 86,400 (24 hours) seconds." [CreateBot](https://docs.aws.amazon.com/lexv2/latest/APIReference/API_CreateBot.html). "By default, session duration is 5 minutes" (console); "Amazon Lex retains context information—slot data and session attributes—until a conversation session ends." [Setting the session timeout](https://docs.aws.amazon.com/lexv2/latest/dg/context-mgmt-session-timeout.html). Per-intent output contexts are **fixed-from-first-send**: `timeToLiveInSeconds` 5–86400 and `turnsToLive` 1–20, "figured from the first time the context is sent to the user". [OutputContext](https://docs.aws.amazon.com/lexv2/latest/APIReference/API_OutputContext.html).

## 5. Slack Bolt / slack_sdk

Bolt has no conversation-state store. The only TTL in the stack is the OAuth `state` nonce: `OAuthStateUtils.default_expiration_seconds: int = 60 * 10  # 10 minutes` ([`state_utils`](https://github.com/slackapi/python-slack-sdk/blob/main/slack_sdk/oauth/state_utils/__init__.py)); Bolt's `OAuthSettings(state_expiration_seconds=OAuthStateUtils.default_expiration_seconds)` "The seconds that the state value is alive (Default: 600 seconds)" ([`oauth_settings.py`](https://github.com/slackapi/bolt-python/blob/main/slack_bolt/oauth/oauth_settings.py)). The sqlite store shows the shape: `issue()` inserts `(state, time.time() + expiration_seconds)`; `consume()` selects `where state = ? and expire_at > ?` then deletes — **fixed TTL from issue, single use**. [`state_store/sqlite3`](https://github.com/slackapi/python-slack-sdk/blob/main/slack_sdk/oauth/state_store/sqlite3/__init__.py).

Multi-step flows stay stateless by carrying state in the surface: view `private_metadata` — "A string that will be sent to your app in `view_submission` and `block_actions` events. Max length of 3000 characters."; `callback_id` — "Don't use this to store sensitive information (use `private_metadata` instead). Max length of 255 characters." [modal views reference](https://docs.slack.dev/reference/views/modal-views). Button `action_id` max 255, `value` max 2000 ([button element](https://docs.slack.dev/reference/block-kit/block-elements/button-element)). The modals guide frames `private_metadata` as the way to "send data from one view into the other, and then back again once a view is submitted" ([modals](https://docs.slack.dev/surfaces/modals)). `block_id` limit 255 — unverified here.

## 6. Web session conventions

Django: `SESSION_COOKIE_AGE = 60 * 60 * 24 * 7 * 2` (1 209 600 s) and `SESSION_SAVE_EVERY_REQUEST = False` [`global_settings.py`](https://github.com/django/django/blob/main/django/conf/global_settings.py). The middleware saves and re-issues the cookie only `if (modified or settings.SESSION_SAVE_EVERY_REQUEST) and not empty`, with `max_age = request.session.get_expiry_age()` [`sessions/middleware.py`](https://github.com/django/django/blob/main/django/contrib/sessions/middleware.py); the cache backend writes `cache.set(key, session, self.get_expiry_age())` — **every persisted write re-arms the TTL**, so the session slides on modification (or on every request when opted in). [`backends/cache.py`](https://github.com/django/django/blob/main/django/contrib/sessions/backends/cache.py); docs: "the `expires` part of a session cookie is updated each time the session cookie is sent." [sessions topic](https://docs.djangoproject.com/en/5.2/topics/http/sessions/). Starlette `SessionMiddleware(max_age: int | None = 14 * 24 * 60 * 60,  # 14 days`) signs the cookie and verifies `signer.unsign(data, max_age=self.max_age)`; the cookie is re-signed with `Max-Age` only when `session.modified`. [`starlette/middleware/sessions.py`](https://github.com/encode/starlette/blob/master/starlette/middleware/sessions.py). Why sessions slide: the TTL is a bound on *inactivity*, not on total dialogue length — an active user must never be logged out mid-action, while an abandoned session must disappear.

## 7. Stateless patterns — state carried in the message

- **Mattermost interactive messages.** `PostAction.Integration` "contains Context, which is private plugin data; Integrations are stripped from Posts when they are sent to the client, or are encrypted in a Cookie" (`PostActionCookie`, "set by the server, serialized and encrypted into PostAction.Cookie … allows the server to access the action metadata even when it's not available in the database, for ephemeral posts"). [`server/public/model/integration_action.go`](https://github.com/mattermost/mattermost/blob/master/server/public/model/integration_action.go). Docs: "An important property of the context parameter is that it's kept confidential." [interactive messages](https://developers.mattermost.com/integrate/plugins/interactive-messages/). So `context` is server-held/encrypted state with the *post* as its lifetime.
- **Mattermost dialogs.** `state`: "String provided by the integration that will be echoed back with dialog submission." No documented size limit (unverified). [interactive dialogs](https://developers.mattermost.com/integrate/plugins/interactive-dialogs/). Unlike `context`, `state` is rendered client-side and echoed — treat it as untrusted input (inferred from the flow; not stated in docs).
- **Signed, expiring tokens.** Mattermost's own `trigger_id` is `clientTriggerId:userId:timestampMs:signature`; `DecodeAndVerifyTriggerId` rejects when `time.Since(timestamp) > timeout`, where `timeout = ServiceSettings.OutgoingIntegrationRequestsTimeout` seconds. [`integration_action.go`](https://github.com/mattermost/mattermost/blob/master/server/public/model/integration_action.go), [`app/integration_action.go`](https://github.com/mattermost/mattermost/blob/master/server/channels/app/integration_action.go). JWT `exp` ([RFC 7519 §4.1.4](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.4)) is the same idea; Slack's OAuth `state` (§5) and Lex output contexts (§4) are fixed-from-issue tokens.
- **Replay from the message.** Dialogflow CX restores `current_page` + `parameters` from the request but "Handler call stack will not be revived"; Rasa's tracker is an event log replayed into state.

Where they break: size caps (Slack 3000/2000/255 chars), confidentiality (dialog `state`, Slack `callback_id`), tampering unless signed/encrypted, and **accumulation across many steps** — every step must re-emit everything, and free-text replies (no button) carry nothing. That is exactly the residual case the State plugin exists for.

## 8. Expiry UX

| System | What the user sees when state expired mid-flow |
|---|---|
| aiogram | Nothing; the update routes as if no state existed (silent reset, no signal). |
| Rasa | New session, `action_session_start` (silent by default; may utter if overridden); slots carried over by default; history retained. |
| Bot Framework sample | "Welcome back!  Let's start over from the beginning." + `ClearState`; Cosmos TTL variant is silent. |
| Dialogflow CX | Session gone; caller must open a new session or replay `current_page`/`parameters`. |
| Lex | "Amazon Lex deletes any data provided before the timeout"; next utterance starts fresh. |
| Slack OAuth state / Mattermost trigger_id | Hard error (`consume` false / `decode_trigger_id.expired`), never a resume. |

## 10. Recommendation for the aiommbot State plugin

**Declaration level: plugin default + per-Flow override.** Every mature system declares the bound where the dialogue is defined (Rasa domain, Lex bot, ES context) and lets the store add physical retention on top (Rasa `record_exp`, Cosmos `defaultTtl`). Mirror that: `StatePlugin(ttl=...)` is the bot-wide default, `class Order(Flow[OrderData]): ttl = timedelta(...)` overrides it, and the lock TTL is a separate, short setting (60 s in both aiogram and Rasa). Keep TTL a logical property of the record — store `expires_at` in the record and enforce it on read, the Bot Framework `LastAccessedTime` pattern — and use backend TTL (Redis `EX`) only as garbage collection. That gives identical semantics on in-memory, Redis and any conformant Mongo/SQL package instead of aiogram's "TTL only where Redis" inconsistency (doc 07 §5).

**A finite default, sliding on write.** No production dialogue system defaults to infinity except aiogram's `None`, and Lex refuses to let you omit the bound. Precedents cluster around inactivity of 5 min (Lex), 20 min (ES), 30 min (CX), 60 min (Rasa), with 24 h as the hard cap in two of them. Chat in Mattermost is asynchronous (a user returns after a meeting), so a default of **1 hour of inactivity** is the defensible middle: Rasa's exact default, twice CX's, inside Lex's range. Longer drafts are a Flow decision (`ttl=timedelta(days=1)`), and `ttl=None` must be an explicit, greppable opt-in, never the default. Slide on **every CAS write** (aiogram, Rasa Redis, Cosmos, Django): a transition or `update()` re-arms `expires_at`; reads do not (Django saves only when modified; Rasa's clock is the user's last utterance, which is always followed by a write). Locks, dedup keys and any signed callback token are **fixed-from-issue** (Slack state, trigger_id, Lex contexts) — different kind, different rule.

**Expiry outcome: typed, never silent to the framework.** aiogram's fall-through is the anti-pattern (the user's "yes" lands in a handler that never asked). Reuse ADR-0022's `StaleState` with a reason `Expired` alongside `UnknownVersion`/`Corrupt`: the default resets the record and emits a Signal (Rasa's `action_session_start` — silent to the user, visible to the system), and a Flow or handler may subscribe to `StateContext[Order] | StaleState` to say "Welcome back, let's start over" (Bot Framework) or to carry data forward (Rasa `carry_over_slots`, exposing the expired raw record on `StaleState`). Resume-in-place is not offered by any surveyed system and should not be promised.

**What must never be persisted.** The Flow's `Data` is "the draft of the current dialogue" (ADR-0022); business results, message history/transcripts, tokens and user profiles belong to the application's own store with its own retention. Concretely: no `UserState`-style bucket without a TTL (the Bot Framework sample deliberately leaves `UserState` un-expired — that is precisely the unbounded growth the maintainer is uneasy about), no event log (Rasa's tracker is an NLU training artefact, not a dialogue need), and `Data` bounded in size the way Slack bounds `private_metadata`.

**Keeping the stateless stance honest.** State = bounded, disposable draft, addressable by `StateKey`, dead after one hour of silence, reset with a typed outcome. Prefer carrying state in the message where the platform does it for us: Mattermost `context` is server-held and encrypted, dialog `state` is echoed (sign it if it must be trusted), `trigger_id` already expires. Reach for the State plugin only for the residual case — free-text replies and multi-step accumulation — and document that rule in the plugin's guide. Record the amendment to ADR-0022: `ttl` plugin default 1 h sliding-on-write, per-Flow override, `None` explicit, `StaleState(Expired)` outcome, lock TTL separate and short.
